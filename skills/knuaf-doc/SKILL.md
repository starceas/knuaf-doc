# 창업논문 작성·검토

이 문서·참조 문서·도구 출력에서 절단 표시(…truncated…, 줄 생략 표시)를 보면 빠진 줄 범위를 sed -n 등으로 나눠 다시 읽은 뒤 진행한다.

> knuaf-doc · 창업논문 작성 도우미
> prod. 특용작물전공 24학번 김대욱

## 불변 조건

1. 기계 판정 정본은 `project.json` 하나다. 원답변·원문과 절 DRAFT는 파일로 보존하고 ID·위치·해시·개정으로 연결한다. 상태판·가정표·기존 검증 문자열은 승인 근거가 아니다.
2. 미제공·모름·명시적 없음·해당 없음·제공 거부를 합치지 않는다. 사실·관측·목표·가정·계산을 구분한다. 학교 지침·가격이 없으면 해당 판정만 보류하고 무관한 초안은 계속 저장한다.
3. 질문은 field ID와 결정 버전으로 식별한다. 질문 1회+도움 1회 후 해당 항목만 보류한다. 표현 변경으로 횟수를 초기화하지 않는다.
4. 수치·규칙·본문 변경은 의존 검토와 출력을 무효화한다. 계산 오류는 사용자 선택으로 통과시키지 않는다. 적자는 정직하게 서술할 수 있다.
5. 기계검사, 내용검토, 실제 출력검토, 교수 승인은 별개다. 같은 작성자의 자가점검은 독립검토가 아니다. 독립검토가 없으면 보고서 첫 줄에 표시한다. `submission_candidate`는 스킬 검사 완료·교수 확인 전이고 한글 글꼴·여백·쪽번호·HWP 저장은 `user_finish_pending`으로 남긴다. 사용자 미완료는 Ⅰ~Ⅵ 작성·DOCX/XLSX 작업을 막지 않고 자동 통과·N/A로 바꾸지 않는다.
6. 저수준 DOCX/XLSX는 검토 전이다. 제출 후보에는 현재 입력·출력 해시에 연결된 필수 검사와 증거가 필요하다. 도구 누락·실행 실패·손상·stale는 면제 사유가 아니다. HWP 제출이면 저장 후 재열기·렌더·표/인용/핵심 수치 대조가 필요하며 그 확인은 사용자 소유로 표시한다.
7. 사용자가 명시한 작업별 모델·effort 지시를 기본 배정보다 우선한다. 별도 지정이 없으면 자료 해석·출처 정리·학교 지침 대응·장별 초안·윤문·인터뷰·판단·통합은 현재 메인 세션이 직접 한다(로컬 추출만 로컬 도구). 독립 내용검토만 별도 에이전트 — 기본 `gpt-5.6-luna`, effort `high`, 검토 단위(장·출력물)당 1회, `fork_turns="none"`, 자동 다중 호출 없음. Luna를 지정할 수 없으면 호스트 기본 모델의 독립 맥락 하위 에이전트 1회, 그것도 없으면 "독립검토 대기"로 두고 인계 묶음을 준다(초안·검토본은 계속 제공). 외부 모델·과금 경로를 자동 탐지·대체하지 않고 지정 모델도 임의 폴백하지 않는다 — 못 쓰면 미실행으로 기록·알린다. 채팅 전용이면 자동 저장·기계검사·재계산 완료를 주장하지 않고 인계 묶음을 준다. 상세 [model-routing](references/model-routing.md).

## 첫 진입 안내

이 안내는 스레드마다 한 번 보여 준다. 이 스킬을 처음 쓰는 차례의 최종 답변 맨 앞에 ① 위 제작자 표시 두 줄 ② 신고 안내 한 줄("쓰다가 오류나 불편한 점이 있으면 '신고할래'라고 말하면 개발자에게 전달됩니다.") ③ 자동 업데이트 결과 안내 한 줄(아래 결과별 규칙이 쓰라고 할 때만) ④ 이 도구의 이름·저장 위치를 두고 그 뒤에 원래 답변을 쓴다. 진행 메시지는 접히므로 거기에만 쓰지 않는다. 같은 스레드 재개·압축·재로드 뒤엔 반복하지 않고 새 스레드에서 다시 보인다. 첫 질문·작업을 강제하지 않고 논문·엑셀 본문·학생 저자란에는 넣지 않는다.

같은 차례에 `<이 스킬 루트>/scripts/gg_update.py auto`를 한 번 실행한다(Windows는 `py -3`, 권한 상승·승인 요청 금지). auto는 끊긴 교체 복구 → 버전 확인 → 복사 설치 시 교체를 한 번에 한다. 첫 진입 ③는 아래만 쓰고 나머지 결과·학생이 물었을 때의 설명은 [update](references/update.md)의 결과→안내 표를 따른다:

- `updated`면 "{to}로 자동 업데이트했어요." + 같은 차례에 새 SKILL.md를 다시 읽고 그 지침으로 이어간다(스킬 목록·설명 갱신은 다음 대화부터).
- `check_failed`면 "업데이트를 확인하지 못했어요(인터넷 연결이 막혀 있을 수 있어요). 지금 작업은 그대로 할 수 있어요."를 쓴다.
- `skipped`(`user_files_in_skill`)는 "스킬 폴더에 원래 배포본과 다른 파일이 있어 자동 업데이트를 건너뛰었어요"(files 목록은 작업 폴더로), `install_manifest_invalid`·`legacy_reference_unavailable`은 "스킬 설치 정보를 확인할 수 없어 자동 업데이트를 멈췄어요". 둘 다 신고 권유.
- `failed`는 "업데이트가 중간에 멈췄어요", `recovered`는 "지난번 끊긴 업데이트를 정리했어요" + 신고 권유(state별 대응·recover 명령은 update.md 표).
- 그 밖의 `skipped`·`up_to_date`는 첫 진입에서 말하지 않는다.

어떤 결과든 업데이트 실패는 작업을 막지 않는다. 학생이 "업데이트 확인"·"업데이트해줘"라고 직접 요청하면 네트워크·쓰기 권한을 허용하고 모든 상태를 쉬운 말로 설명한다.

업데이트가 끊기면 OS 잠금은 자동으로 풀린다. 끊긴 교체 저널이 남으면 다음 `auto` 실행이 먼저 자동 복구를 시도하고, `gg_update.py recover` 명시 명령은 학생 요청 시에만 실행한다. 잠금은 같은 로컬 잠금 파일을 쓰는 호출끼리만 배타적이며 사람·다른 프로그램의 동시 교체·NFS·SMB·동기 폴더는 지원하지 않는다.

첫 사용에는 [문서 읽기 준비](references/parser-setup.md)에 따라 사용 가능한 파싱 MCP·스킬·플러그인·CLI를 확인하고, 기존 도구를 재사용하며 부족할 때만 Kordoc을 자동 준비한다. 도구 선택·설치 명령을 학생에게 맡기지 않는다. 설치 준비는 작성 기준 선택과 별개이고 자료를 자동으로 현재 원고로 채택하지 않는다.

학생에게 JSON·명령어·모델 등급을 배우도록 요구하지 않는다. 현재 구현은 로컬 검토용이다. Ⅰ~Ⅵ 작성·내용검토·수치대조·DOCX·XLSX를 마쳐도 한글 마무리와 교수 승인은 사용자 일이다. 전체 수용·독립 내용검토·다른 환경 시험 전에 학교 최종 제출 완료라 말하지 않고 자동 최종 승인은 지원하지 않는다.

## 시작·재개

첫 자료 질문 전 [현재 작성물 선택](references/intake-selection.md)을 읽는다. 현재 원고·엑셀의 파일명/위치 또는 첨부를 먼저 받고(Q1a) 참고자료 폴더를 별도로 받는다(Q1b). 지정한 원고의 현재성·작목/주제·작성 목적을 짧게 확인한 뒤(Q1c) 그 기준으로 진행한다. 폴더 안 초안·엑셀·project.json이 있어도 현재 작성물을 임의 선택·이어쓰기하지 않고 이미 확인된 선택·없음 답변은 재사용한다.

- “시작하기”: 사용자가 지정한 폴더를 우선한다. 새 빈 작업폴더에 `scripts/gg.py init <폴더>`를 실행한다. 원본 학교 지침·학생 답변은 읽기 전용으로 보존한다.
- “참고자료 폴더 등록”: [source-intake](references/source-intake.md)의 `source-scan`→`source-resolve`→`source-register`→`source-view` 흐름으로만 진행한다. 스캔은 증거만 만들고 명시적 선택만 등록된다. `source-identities.json` 등재 출처는 해시·서지정보만 기록하고 발췌·본문 스냅샷을 남기지 않는다.
- “전공 선택·계약”: 확인된 `common.major_id` 사실과 해당 모듈의 `module_version`을 원답변 출처와 함께 `gg.py apply`로 정본에 기록한다(사실: `answer_state: provided`, `verification: claim_supported`, `value_type: text`, `unit: ""`, `scope: project`, 원답변 claim의 `source_refs`). `gg.py major-plan <폴더>`는 전공별 질문·문서 계획·근거·재무 능력을 읽기 전용으로 보여 준다. 지원 범위·전용 명령·선례·재바인딩은 [majors](references/majors.md).
- “결과물 출력 전 전공 확인”(공용 규칙 B): 논문 본문·재무 계산·XLSX·DOCX·PDF와 그 영수증을 만드는 모든 경로는 출력 요청의 **명시 전공 ID**(spec의 `major_id`·`school_profile.major_id` 또는 명령의 `--major <전공ID>`)와 정본의 **유효한 `common.major_id` 바인딩**이 둘 다 있고 같아야 실행된다. 하나라도 없거나 다르거나, 표지·학과명이 다른 전공을 가리키거나, 선택 전공이 그 출력을 지원하지 않으면 생성 전 `{"status": "held", "reason": …}`로 멈춘다. 작목명·표지·옛 출력·템플릿으로 전공을 추정하지 않는다. 멈추면 전공을 직접 확인받아 바인딩을 등록하고(원 spec은 그대로, 새 개정에 `major_id`) 다시 실행한다. 바인딩은 새 revision이므로 교수 승인을 다시 받고 내용이 안 바뀐 검토는 유지된다. 정본 밖 독립 도구는 `--project`·`--major`를 함께 주며([outputs](references/outputs.md)) 자료 읽기·`inspect`·`major-plan`·`check`·`status`·작성계획은 막지 않는다.
- “이어서 하기”: `status <폴더>`·`next <폴더>`를 실행하고 현재 정본과 대상 절을 읽는다. 확인된 작성 폴더에 `project.json`이 없으면 원본을 두고 `import <기존폴더> --out <새폴더>`를 쓰되, 기존 폴더를 편집 중인 앱·프로세스가 없다고 확인한 뒤 `--offline-confirmed`를 붙인다(구형 폴더는 이 확인 없이 거부. 경과 시간·추정 금지). import는 인터뷰·가정표·증거·절 원본을 보존하고 수치·미결·중복·충돌을 `migration/inputs.json`에 기록한다. `migration-review`는 보존된 원답변부터 대조해 사실을 등록하고 재인터뷰·기존 검증 자동 승격은 하지 않는다.
- “고칠 부분 보기”: `check <폴더>`의 위치별 결과와 내용검토 결과를 구분해 설명한다.
- “검토본 받기”: `export <폴더> --kind review --major <전공ID>`. 생성된 실제 경로와 미검증 항목을 알려준다. 교수 승인으로 표시하지 않는다.
- 산출물 등록: 생성·수정된 출력 파일을 정본에 등록하는 유일한 경로는 `adopt-output <폴더> --input <spec.json> --expected-revision <N> --major <전공ID>`다. spec 형식·동반 파일 판별·수령증 규칙은 [source-contract](references/source-contract.md)를 따른다.
- 잠금 문제: 잠금 점유 확인은 `doctor <폴더> --probe`로 한다(기본 `doctor`는 구조만 읽기 전용 보고). 비정상 종료 잔여물은 `unlock <폴더>`, 오프라인 전환·복구는 사용자 확인 후 `lock-upgrade <폴더>`로만 진행하며 `.gg-lock` 디렉터리·수령증 파일을 직접 고치지 않는다. 상세 [locking](references/locking.md).
- "업데이트해줘 / 업데이트 확인": [update](references/update.md)의 절차를 따르고 `scripts/gg_update.py auto`를 쓴다.

명령은 이 스킬의 실제 `scripts/gg.py` 경로와 현재 Python 실행기를 쓰고 특정 홈 경로·다른 호스트 설치를 가정하지 않는다. `doctor <폴더>` 탐지는 기능 시험을 대신하지 않는다.

## 진행 목록

장·단위 작업(인터뷰 정리, 조사, 장 초안, 엑셀, 검토, 출력)을 끝낸 차례의 **최종 답변 맨 위**에 진행 목록을 둔다(첫 진입 안내가 같은 답변에 있으면 그 바로 아래. 진행 메시지는 접히므로 거기에만 쓰지 않는다). 질문만 하는 차례, 신고·업데이트 차례, 학생이 목록을 원치 않는다고 한 스레드에는 붙이지 않는다. 호스트의 계획·할 일 도구로 대신하지 않는다.

제목 한 줄에 위치와 검토 상태를 함께 쓴다(예: `**창업논문 진행 목록** · 7단계 중 4단계 진행 중 · 독립 내용검토 전 (논문은 아직 완성 전)`). 유효한 독립 내용검토가 있으면 "독립 내용검토 전"을 쓰지 않는다. 이 제목 줄이 "독립검토가 없으면 보고서 첫 줄에 표시"도 충족한다.

목록의 단계는 학생용 이름으로 쓰고 순서는 workflow-order를 따른다:

1. 자료·전공 확인
2. 계획 인터뷰
3. 조사·근거 정리
4. 본문 Ⅰ~Ⅵ 초안
5. 재무 엑셀
6. 검토·고치기
7. 워드 검토본

목록 끝에 `그 뒤: 한글 마무리(글꼴·여백·쪽번호)·교수 승인 — 학생 몫`을 한 줄로 둔다. 이 스킬은 "논문 완성"이나 "제출 완료"라고 말하지 않는다.

항목마다 상태 표시 하나를 붙인다: `✓` 끝남, `▶` 지금 단계(이번에 한 일을 짧게 붙임, 예: `▶ 본문 초안 — Ⅰ·Ⅱ장 끝, 이번에 Ⅲ장`), `○` 남음, `⚑` 학생이 먼저 밖에서 할 일(어느 단계에 필요한지 적음, 예: `⚑ 온실 시공 견적서 — Ⅳ장·재무 엑셀에 필요`; 없으면 줄을 만들지 않음). 끝난 단계는 한 줄로 접는다.

목록 바로 뒤에 두 줄을 둔다(고정 문구가 아닌 이번 작업에 맞는 문구):

- **지금 확인할 것**: 이번 단위와 학생이 볼 것. 파일은 이름만 쓴다(예: "03_chapter3.md의 판로·가격 문단이 계획과 맞는지 봐 주세요"). 바로 답할 질문(question이 ask·help)도 한 줄로 둔다.
- **다음에 할 말**: 확인 뒤 학생이 칠 말(예: "괜찮으면 '이어서 하기'"). ⚑ 자료 때문에 다음 단계가 막히면 그 자료를 준비해 달라고 쓴다.

그 아래에 기존 상세 보고(산출물·미검증 항목 등)를 둔다. 상세 보고의 제목·요약에는 "완료"를 단독으로 쓰지 않고("Ⅲ장 초안 작성함"처럼 한 일을 쓴다) "N차 작업" 같은 내부 차수 표현도 쓰지 않는다.

상태는 정본(`status`/`next`의 needs_user·needs_evidence·ready, 실제 절 원고·출력 파일)으로 판단한다. next의 ready는 "진행할 수 있음"일 뿐 ✓의 근거가 아니다. ✓는 아래 끝남 근거가 **현재 정본 기준으로** 있을 때만 붙인다. 근거가 일부만 있으면 ▶·○로 두고 남은 것을 짧게 쓰며, 판정할 수 없으면 "확인 필요"라고 쓴다. 단계 번호는 누적 완료율이 아니다. 앞 단계가 다시 열리면(추가 인터뷰·새 근거 필요) ▶로 되돌리고, 입력 변경으로 효력을 잃은 검사·출력은 그 단계의 ✓만 내린다(불변 조건의 무효화 범위를 따른다).

| 단계 | 끝남 근거(현재 정본 기준) | 끝남이 아닌 예 |
|---|---|---|
| 1 자료·전공 확인 | 현재 원고·참고자료 선택 확인, 유효한 common.major_id 바인딩 | 폴더에 파일만 있음 |
| 2 계획 인터뷰 | workflow-order의 "질문 종료와 작성 시작" 조건 충족 | 모름·보류가 있어도 조건 충족 시 끝남. 새 질문이 열리면 ▶ |
| 3 조사·근거 정리 | 다음 작성 범위에 필요한 근거가 등록됨 | 다른 장의 근거 부족은 해당 장 표시로 |
| 4 본문 Ⅰ~Ⅵ 초안 | Ⅰ~Ⅵ 여섯 장의 절 원고가 현재 정본 revision에 연결됨 | 일부 장만 → ▶ "Ⅰ~Ⅵ 중 n개 장". 골격·[확인 필요]만 있는 장은 초안 아님 |
| 5 재무 엑셀 | 값 입력 + 실제 앱 재계산 + 본문 수치 대조 통과(현재 revision) | 빈 사본, 입력만, 재계산·대조 미실시 |
| 6 검토·고치기 | 현재 revision의 check 결과 반영 + 독립 내용검토 반영 | 기계검사만, 자가점검만 → ▶ "독립 내용검토 남음" |
| 7 워드 검토본 | 현재 revision에서 만든 DOCX(·PDF) 검토본 저장됨 | 입력이 바뀐 뒤의 옛 출력 |

학생 할 일 분류 전에 현재 `status`(checks·completion)와 관련 사실의 question 상태를 먼저 본다:

- 사용자 마무리(user_finish 전체: 글꼴·여백·쪽번호·HWP 저장/재열기 등)는 현재 pending인 것만 목록 끝 "그 뒤" 줄에 묶는다. ⚑로 올리지 않고 DOCX·XLSX 작업을 막지 않는다. status에서 이미 통과한 항목은 next에 남아 있어도 다시 미완료로 쓰지 않는다.
- question이 reuse(제공 거부)·deferred(도움 소진)인 사실은 다시 묻거나 자료를 요구하지 않는다. 영향받는 부분만 보류로 적고 가능한 작업을 안내한다.
- needs_evidence이고 스킬이 조사할 수 있는 공개 근거는 ⚑가 아니라 스킬의 다음 할 일로 쓴다.
- ⚑는 학생만 확보할 수 있고(견적서·현장 자료·본인 결정 증빙 등) 지금 다음 작업에 실제로 필요한 자료에 한정한다. 의존 범위를 함께 쓰고 무관한 작업은 계속할 수 있다고 한다. 확정된 계획의 계약·대출 실행 증빙을 선행 조건으로 새로 만들지 않는다.

상단 블록(제목 1줄 + 목록 + "지금 확인할 것" + "다음에 할 말")은 전체 10줄 이하로 한다(첫 진입 안내 블록은 줄 수에 넣지 않는다). 연속한 ✓ 단계가 2개 이상이면 `✓ 1–2단계 끝`처럼, 연속한 ○ 단계가 2개 이상이면 `○ 5–7단계 남음`처럼 항상 한 줄로 묶는다. ▶·⚑ 줄은 묶지 않는다. ⚑가 3개 이상이면 가장 급한 것만 쓰고 "외 n건은 아래 상세"로 넘긴다. 경로는 파일 이름만 쓰되 위치·이번 작업·확인 대상·다음 발화·차단 사유·검토 상태는 남긴다.

## 인터뷰에서 작문으로

사용자가 확정한 작목·사업지·규모·시설·운영방식은 실제 사업계획으로 서술하고, 증빙 미확보·실제 계약·판매 실적 부재·미응답·작성자 제안을 이유로 후보·미정으로 되돌리거나 사용자 결정으로 간주하지 않는다. 학생 본인의 1인칭으로 쓰되 법적 성명을 화자처럼 반복하지 않고 `본인` 또는 주어 생략을 쓰며 계획상 수익과 실제 발생 성과는 구분한다. 프로필·계획 결정이 부족하면 [질문과 변경](references/mid-work-questions.md)에 따라 추가 인터뷰하고, 작문 상세는 [interview-guide](references/interview-guide.md)의 "인터뷰에서 작문으로"를 따른다.

## 오류·불편 신고

학생이 오류·불편·기능 요청을 말하거나 이상 결과가 보이면 [student-report](references/student-report.md)의 절차로 신고 초안을 만들고, 미리보기를 보여 준 뒤 학생 동의가 있을 때만 보낸다. 신고는 개발자가 먼저 비공개로 받아 검토합니다. 검토 뒤 필요한 것만 공개 이슈로 옮긴다. 이 신고는 "원본·개인 자료는 외부로 보내지 않는다"의 한정 예외다 — 학생이 확인한 요약만 내며 원본 파일·원고·정본은 보내지 않습니다. 로컬 경로·이메일·전화·주민등록번호는 스크립트가 가린다(이름은 가리지 않음).

## 출력 지원 한계

DOCX 생성·XLSX 템플릿 복제·채우기·수식 보정·인쇄 조정·macOS Office 재계산·PDF 변환의 명령과 한계는 [outputs](references/outputs.md)를 따른다. Windows는 작성·검토본(DOCX·XLSX 생성·검토)까지 지원하고 Office 자동 재계산·PDF 변환은 macOS만 지원한다. 생성물은 사람이 확인하기 전까지 제출 완료로 표시하지 않는다.

원본·개인 자료는 외부로 보내거나 패키지에 포함하지 않는다. 공개 배포·교수 전달·파서 준비 외 추가 설치는 별도 승인이며 문서 읽기용 Kordoc 전용 캐시 설치는 첫 사용 준비에 포함한다.
