# 첫 사용 문서 읽기 준비

사용자 결정 2026-09-07: 학생은 파서·MCP 개념이나 설치 명령을 배울 필요가 없다. 스킬이 기존 문서 읽기 도구를 확인하고, 필요한 경우에만 준비해 읽기를 실행한다. 필요한 도구의 자동 준비는 첫 사용에 포함하며, 학생에게 같은 설치 선택을 반복해서 묻지 않는다. 호스트·운영체제가 직접 요구하는 권한 화면은 우회하지 않는다.

## 자동 준비

**설치보다 기존 도구 확인이 먼저다.** 학생에게 도구 종류나 설치 여부를 묻지 않고 스킬이 다음 순서로 확인한다.

1. 현재 호스트의 연결된 MCP·스킬·플러그인에서 문서 읽기를 확인한다. 실제로 호출해 대상 파일의 글·표·원문 위치 등 필요한 내용을 얻을 수 있는 도구만 쓴다. 이름만 등록됐거나 비활성·호출 불가한 도구는 읽기 기능으로 세지 않는다. 숨겨진 전체 홈 폴더나 다른 작업의 설정·인증정보를 광범위하게 검색하지 않는다.
2. 연결된 도구가 없거나 필요한 읽기를 지원하지 않으면 DOCX·PDF·XLSX는 확인 질문 없이 동봉 Python 읽기를 먼저 준비하고 사용한다. `gg_deps.py doctor <작업폴더>`를 실행하고 준비 상태를 확인한다. 읽기 패키지가 없으면 `gg_deps.py ensure <작업폴더>`로 작업 폴더의 `.venv`에 필요한 Python 패키지만 준비한 뒤 `gg_deps.py python <작업폴더>`가 돌려준 인터프리터로 `gg_read.py <선택한-파일> --out <새-결과.md>`를 실행한다. Node나 Kordoc 준비를 기다리지 않는다. 준비가 안 되면 그 사유를 기록하고 이 파일을 읽지 못했다고 알린다. OCR·그림·쪽 배치·복잡한 표 구조를 보존한다고 추정하지 않는다.
3. HWP·HWPX 등 Python 읽기 범위 밖의 형식은 기존 파싱 도구를 먼저 확인하고 실제로 읽기 검증한다. 연결된 도구가 없거나 필요한 기능을 지원하지 않을 때는 기존 계약대로 `scripts/gg_kordoc.py ensure`가 PATH의 호환 CLI를 확인한 뒤 전용 캐시를 준비한다. 읽기에는 Node.js 20 이상이 필요할 때만 호스트에서 실제 실행 경로를 확인해 전달한다. DOCX·PDF·XLSX의 첫 Python 읽기는 이 준비 때문에 기다리지 않는다.
4. Python 읽기로 DOCX·PDF·XLSX의 스캔 글자·그림 안 글자·복잡한 배치가 필요한 요청까지 처리할 수는 없다. 읽기할 수 있는 범위를 결과에 남기고 부족한 형식·내용만 보류한다. OCR 모델이 필요한 경우에는 자동 설치·전송 승인을 추정하지 않는다. 기존 도구·전역 패키지·다른 프로젝트 의존성·MCP 설정을 바꾸지 않는다.

재사용 여부는 형식·작업별로 판단한다. PDF를 읽었다고 HWP나 병합 표까지 지원한다고 추정하지 않는다. 이미지 OCR이나 온라인 업로드가 필요한 도구는 기존 설치가 있다는 이유만으로 추가 다운로드·외부 전송 승인을 얻은 것으로 간주하지 않는다. 원문 손상·잘못된 경로·권한 오류를 기능 부족으로 오인해 같은 파서를 중복 설치하지 않는다. 실패 이유가 불명확하면 관련 읽기만 보류하고 가능한 작업을 계속한다.

선택한 도구의 실제 호출 경로, 지원/미검증 형식, 입력 해시와 결과 위치, 재사용 또는 신규 설치 사유를 작업폴더의 감사 기록에 남긴다. 기록은 현재 실행 증거에 연결하고, 이름만 적거나 오래된 성공 기록만으로 준비 완료라고 말하지 않는다.

기존 도구가 바로 실행되면 Node.js·pnpm 탐지나 설치를 추가로 요구하지 않는다. 기존 CLI 실행에 Node.js만 부족하거나, 새 전용 캐시 설치에 필요한 Node.js·pnpm이 없을 때에만 호스트의 번들 실행환경 조회 도구를 사용한다. Codex Desktop에서는 `load_workspace_dependencies`가 제공되면 조회하여 반환된 Python·Node·pnpm의 실제 경로를 사용하고 `--node`, `--pnpm`으로 전달한다. 고정된 개발자 홈 경로를 복제하지 않는다. 다른 환경에서는 실제 제공된 런타임을 확인한다. 사용 가능한 실행환경을 찾지 못하거나 네트워크·권한에 막히면 실패 이유와 필요한 조치를 짧게 알리고, 인터뷰와 이미 읽을 수 있는 자료 작업은 계속한다. 설치되지 않았는데 준비 완료라고 말하지 않는다.

설치 성공은 문서 파싱 성공이 아니다. 실제 확인된 자료를 처음 받을 때 아래 읽기 검증을 수행한다. 자료가 아직 없으면 읽기 검증은 미실행으로 남기며 임의로 폴더의 옛 원고를 고르지 않는다.

## 자료 읽기

`DOCX·PDF·XLSX`의 동봉 Python 읽기는 `python3 <스킬>/scripts/gg_deps.py python <작업폴더>`가 돌려준 인터프리터로 `scripts/gg_read.py <선택한-파일> --out <작업폴더-안의-새결과.md>`를 실행한다. 이 명령은 입력 파일 하나만 읽고 원본을 바꾸지 않으며, 기존 결과 파일을 덮어쓰지 않는다. 표준 출력의 결과 기록에는 입력·결과 위치와 SHA-256, 읽은 값, 형식별 보존 한계가 포함된다. `status: read`만 읽기 성공이다. 스캔·빈 페이지가 있는 PDF는 `incomplete`, 손상·암호화·미지원 파일과 읽기 실패는 `blocked`다. 실패나 일부만 읽힌 문서를 성공으로 바꾸지 않는다. 학생에게는 결과와 필요한 다음 할 일만 말한다.

기본 보존 범위는 DOCX 문단·표의 순서와 셀 글, PDF에서 선택 가능한 글자와 PDF 쪽 순서, XLSX 셀 주소·값·수식이다. 페이지 배치·그림 안 글자(OCR)·각주/머리말/꼬리말·복잡한 병합 표 모양·엑셀 서식/차트·수식 재계산은 보장하지 않는다. 필요한 표·수치는 원본과 직접 대조한다.

파서가 읽은 결과로 사용자의 목적·파일 소유권·현재성을 대신 결정하지 않는다. 도구 선택·실행에 사용한 경로, 형식·제한, 입력 해시와 결과 위치는 작업 기록에 남긴다.

문서는 로컬에서 처리한다. Python 읽기와 Kordoc 읽기는 원문 업로드·클라우드 OCR·모델 공급자 호출을 하지 않는다. 스캔 PDF는 자동 성공으로 표시하지 않고 OCR도 하지 않는다. 손상·암호화·미지원 파일은 읽지 못했다고 남긴다. 추가 OCR 모델 설치는 별도 범위와 권한을 확인한 뒤 처리한다.
실행 요약에는 결과 상태, 실제 입력·결과 경로, 두 파일의 해시, 형식별 읽기 개수와 제한을 남긴다. 읽기에 성공했더라도 원문 해시가 바뀌거나 추출할 글·표·값이 없으면 `incomplete`로 두며 완료로 보고하지 않는다.
## MCP와의 관계

기존에 사용할 수 있는 로컬 파싱 MCP·스킬·플러그인을 먼저 재사용한다. Kordoc은 CLI와 MCP를 제공하며 새로 준비해야 할 때의 기본 경로는 로컬 CLI다. MCP 재등록·대화형 setup·앱 재시작을 첫 인터뷰의 필수 조건으로 만들지 않는다. 이미 연결된 Kordoc MCP도 실제 동작을 확인하면 사용할 수 있지만, 설치 표시만으로 문서를 읽었다고 주장하지 않는다.

확인한 공식 출처: [Kordoc 저장소](https://github.com/chrisryugj/kordoc), [CLI와 MCP 사용법](https://github.com/chrisryugj/kordoc/blob/main/README.md). 스킬 릴리스마다 검증한 정확한 버전만 설치하며 업데이트는 별도 검증 후 바꾼다. 기존 설치는 필요한 기능을 확인해 재사용한다.

문서 읽기용 Python 패키지 `python-docx`·`pypdf`·`openpyxl`은 이미 선언된 [runtime dependencies](package-install.md)를 사용한다. 선택한 Python에서 이 패키지를 불러오지 못하면 읽기를 보류하고, 설치되지 않았는데 읽었다고 말하지 않는다. XLSX·DOCX·PDF 생성과 출력 검증의 준비·설치 계약은 별도로 [package-install.md](package-install.md)를 따른다.

## 기존 원고를 장별로 나누기

파서가 만든 Markdown·텍스트 또는 DOCX 원고를 공식 목차에 따라 절 초안으로 나누려면 `python scripts/gg_draft_split.py <작업폴더> --from <원고.md|txt|docx> --toc <목차.json>`을 사용한다. HWP/HWPX는 먼저 위 문서 읽기 준비 절차로 Markdown/텍스트로 변환하고 표·본문 순서를 확인한다. 목차 JSON은 절 ID·제목·정규식을 포함하며 `--toc`으로 전달한다. 도구는 목차나 장 구성을 하드코딩하지 않는다.

기본 실행은 쓰기 없는 분할 계획만 출력한다. 제목 중복·순서 오류·표 안의 제목·첫 제목 전 본문은 `held`로 남기며 `proposed`만 적용할 수 있다. 계획을 검토한 뒤 `--apply --plan <확정-plan.json> --from <같은-원고> --change-out <작업폴더-안-변경.json>`으로 초안 파일과 `gg.py apply` 입력을 만들고, 이어서 `gg.py apply <작업폴더> --change <변경.json> --expected-revision <현재 revision>`으로 정본에 등록한다. 원본은 `sources/imported/`에 보존하고 기존 절 파일은 덮어쓰지 않는다. 분할은 사실 확인이나 검토 완료가 아니다. 표는 한 덩어리로 유지하며 병합 셀·그림·각주·복잡한 레이아웃은 원본과 별도 대조한다.
